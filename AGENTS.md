# PearTube Development Guide

PearTube is a decentralized CDN and debrid provider on the Holepunch stack. The core is deliberately small: the Holepunch modules do the heavy work, and PearTube glues them together. Keep it under 1,000 lines.

## Agent Instructions

Builds, installs, and deploy commands may be run when explicitly requested.

## Layout

|File|Purpose|
|---|---|
|`src/index.js`, `src/mnemonic.js`|`createNode`: Corestore, unified ACL-gated Autobee Channel + deterministic `apply` (read-only `optimistic: false` followers, fork-proof 12/24-word BIP-39 `claim` device linking in `identity.json` `0600`, `grantWriter`/`revokeWriter` roles `owner`/`mod`/`writer`, owner/mod cross-writer deletion, and XSalsa20 `EpochKey`-wrapped per-video Hypercore encryption via `peartube://access/…` passes), 1-Hypercore-per-video `Hyperblobs` (`512 KiB` blocks at `blockOffset: 0` with lazy Corestore wakeup, plus backwards-compatible legacy shared `blobSlots` reads), `rechunkLegacyBlobs` (`foreground` override, non-blocking clear), Hyperswarm, `search` / `put` / `append` / `publish` / `remove`, and `setLan` to swap LAN discovery without restarting the node. A `createNode` that throws closes everything it had opened (store, channel, swarm, timers, LAN, blob server), so the same storage opens again; LAN discovery that cannot start at open is logged and skipped, not fatal|
|`src/blob-server.js`|Leak-free HTTP Range streaming over `hypercore-byte-stream` (`prefetch: false`, `2 MiB` `highWaterMark`) with one smooth sliding `core.download` window (`96 MiB` on mobile worklets, `256 MiB` on macOS desktop & relays; inactive `active: false` sessions on owned local cores) and hard stream/download cancellation on socket close, aborted async `resolve`, or `clearCache()` — plus a token-guarded LAN instance in `src/cast.js` for TV receivers. `/v1/blob` in `src/http.js` proxies to it over loopback for the same-origin web player|
|`src/acquire.js`|Private job queue: fetch a source with 30 s stall timeouts, cross-origin redirect auth stripping, `Range: bytes=offset-` mid-stream resume (`If-Range`), and terminal `4xx` dead-lettering (downloading and muxing page links through `ubit` on every attempt, since their media URLs expire), `put` it into a dedicated `512 KiB` per-video core, save the announce immediately without touching foreign cache, `append` it durably, and `repointBlob` on legacy slot migration. Stored in `jobs.json`, never in the Corestore|
|`src/settings.js`|Relay settings: `settings.json` (private, `0600`, beside `jobs.json`), then env var, then default; an env var is a starting value the UI can override, and `null` puts it back. Every key is flagged `live` (applied in place) or not (applied by reopening the node in-process); `restartNeeded` lists only values the running node does not use, i.e. after a failed reopen. Secrets and tokens inside URLs never leave the file: views carry `{ref, label}`, and `#n` keeps a stored URL on update. `bin/relay.js` reads every non-bootstrap option through it. It also saves a founded tracker's key as `tracker` (`remember`): `createNode` keeps its own tracker primary only when given that key or no saved sources, so a bare-started relay that follows a channel would otherwise lose its library on the next start|
|`src/identify.js`|What a link holds, before acquiring it: a direct file (name parsed for title, year, `SxxEyy`, resolution, codec, audio) or a page read by `ubit info --json` (title, author, length, thumbnail) and downloaded by `ubit get --json`. Movie- or episode-like names get Cinemeta suggestions (`PEARTUBE_CINEMETA_URL`); an exact title and year is `match`. Accepted ids are `imdb:tt…` / `imdb:tt…:sNNeNN` with `Name Year` / `Name S01E02` titles, the shapes MediaStorm searches for; anything else is a `clip:` id. Imported by `bin/relay.js` and `src/acquire.js` only, so the apps' worklet never packs `bare-subprocess`|
|`src/http.js`| HTTP (`:8174`) and optional `bare-https` (`:8443` when `tls.crt` + `tls.key` exist in storage): the UI at `/`, `/ca.crt` (`ca.crt` download for LAN Root CA trust), `/v1` API (including `/v1/settings`, and `/v1/identify` + `/v1/poster/:tt` when the relay provides them), `/v1/blob` same-origin HTTP Range blob streaming, `/web/*` WASM player assets, and the Stremio add-on (`/manifest.json`, `/catalog/…`, `/stream/…`), serving `COOP: same-origin` + `COEP: credentialless` + `CORP: cross-origin` so secure contexts (`localhost` / `https://`) unlock `crossOriginIsolated` and `SharedArrayBuffer` without breaking cross-origin `302` Cinemeta poster images or Stremio CORS. Unwraps `req.socket.socket.remoteAddress` under `bare-https` for LAN settings and matches `http`/`https` scheme on Stremio catalog/stream URLs. Catalogs list only `tt` ids (the add-on serves no `meta`) with posters through `/v1/poster`; streams carry `notWebReady`, `videoSize`, the episode's `SxxEyy` in the title, and the resolution in the name (`PearTube (Local)\n1080p`), which ranking clients such as MediaStorm need: without it MediaStorm put PearTube 95th of 97 and cut it at 50. Stream URLs are `/v1/blob` on the `Host` the client used, not the blob server's port: MediaStorm admits a private address only for its configured add-on's origin and refused `:8175`|
|`src/resolution.js`|A video's picture size from its container header (Matroska/WebM, MP4/MOV with `moov` anywhere, AVI), read through the node's own blob server once per stream and cached; a file that gives none is tried again after 10 minutes. Tiers go by width first, so 1920x800 is 1080p; standard definition is 480p, and smaller pictures are named by their height (`384p`)|
|`src/ui.js`|The relay web UI (one HTML string): Library (one add box for links, pages and `peartube://` links, with identification preview; folder, feed and channel-copy panels; jobs; a poster grid filtered by kind, 60 tiles at a time and redrawn only when its contents change, with a details sheet listing a show's episodes by season), Channels, Sharing (peers, kept copies, HiveRelays, Stremio/M3U), TV (pair, remote, browser TV) and Settings tabs. Plugins appear only as user intents, never by id; light and dark themes; in-browser `peartube-media` WebAssembly playback. On the Settings tab every edit (text, switch, list entry, "Use PEARTUBE_…") waits in its card's draft until that card's Save; saving one card redraws only it, so other cards keep unsaved edits. The Sharing tab's switches are one-click intents and apply at once. The page is one template string: no backticks in its script, comments included|
|`web/`|Browser WebAssembly player (`peartube_web.wasm`, `sh web/build.sh` -> `web/assets/`, not part of the core line budget): compiles `peartube-media`'s containers, software decoders, surround downmixer, subtitle decoders, and low-latency CMAF fMP4 muxer to `wasm32-unknown-unknown` (`+simd128`) inside a Dedicated Web Worker. MSE gets H.264/HEVC/AV1/VP9 as fMP4 and VP8 as WebM (Chromium refuses `vp08` in MP4); the manifest's `mseType` is the full MIME the page probes and opens its SourceBuffer with. A LAN relay page over plain HTTP is not a secure context, so it has no WebCodecs (`VideoDecoder`) and no shared-memory threads: there, MSE and single-threaded Wasm are the only video paths. `src/decode_order.rs` is the native player's decode-order repair vendored at the pinned media revision and wrapped around every demuxer `pt_open` builds: H.264/HEVC files whose MP4 carries no `ctts` get presentation timestamps from picture order counts before the software decoder, WebCodecs, or the MSE muxer reads them. The Worker keeps six 2 MiB blocks (12 MiB, three in flight) of read-ahead in a 64 MiB ring: a 15 Mbps title decodes at ~3.8x realtime while filling its buffer, and a shallower window fell through to the blocking sync read, freezing the frame clock and dropping pictures once a read took 300 ms. The Worker also drains its queue estimates at wall speed and re-pumps on its own timer when the page's playback credits stop: those credits ride the page's `requestAnimationFrame`, so a hidden, unfocused, or occluded window used to leave the buffers "full", stop decoding, and pause playback after a few seconds (the UI E2E hides a clip for 12 s and now keeps its sound). Bitmap subtitle decoders (`dvd_subtitle`/PGS/DVB) are created with the video stream's dimensions, not the subtitle stream's absent or dummy size, so a DVD cue authored at 758,709 on a 1920x816 picture paints inside the canvas instead of falling off a 720x576 default. Software video is drawn by the page-side GL canvas, not the Worker's OffscreenCanvas: the Worker's render loop measured ~18 of 24 pictures on Batman's VC-1 where the page path holds 24 over the same relay, and the page path carries the detected letterbox crop too (Batman's 1080-row frame crops to 1920x801, so the picture fills the stage width). The clock text and seek bar are written only when their formatted value changes; rewriting the same text node every animation frame made the clock shimmer. On every return the page hard-snaps the MSE element to the audio clock (a background-muted `<video>` and rapid hide/show left it drifting) and drops stale software pictures, and a click on an unfocused window (or within 900 ms of returning) does not toggle play — it only focuses the window. The page owns read-ahead: it fetches 2 MiB blocks with a 6 s timeout and retry and posts them to the Worker, and the Worker's own fetch loop is gone so the two never starve the browser's six connections; a miss still falls back to a 2.5 s sync Range read (never more), and an empty body is an error, not an end of stream. A picture stalled >1.2 s shows "Buffering…". Hidden pictures are retained in a 72-frame ring (the newest is the live one, so the first tick after return draws instantly — measured ~130 ms) instead of being discarded; the MSE SourceBuffer keeps filling while hidden and the element is snapped inside the live buffered range. The Worker's wasm heap measured flat at 29.6 MB over 70 s visible and 60 s hidden, with the block cache (32 x 2 MiB) and buffer pools bounded — the leak was JS-side picture queueing, not the Rust engine The crate root denies `unsafe_code`: `ffi.rs` (host bridge, allocator, raw-pointer marshalling, SIMD128 loads) and `abi.rs` (the C exports) are the only unsafe, and the demuxers, decoders, mixer and muxer are safe Rust. |
|`src/lan.js`|Optional zero-wrapper LAN discovery directly over an isolated ephemeral `HyperDHT` (`port: 0`) + mDNS (`bonjour-service`), stamping each peer's advertised address (`h`) so peers dial directly rather than an mDNS reflector, rebrowsing every 10 s for missed Wi-Fi multicast answers, and falling back to dialing from the larger-key side after 3 s when a host firewall blocks incoming UDP. Every advertisement gets a fresh name (3 random characters in its generation): bonjour-service does not throw on a taken name, it logs "Service name is already in use" and silently stops the advertisement, and a name used before can still be answered for. `bin/relay.js` passes it to `createNode` as a factory; `lanAddress` picks Wi-Fi/Ethernet IPv4 and `interfaceAdapter` pins multicast to that interface. `interfaceAdapter` shares one refcounted multicast socket per interface across the process: LAN discovery, the cast receiver's advertisement and the cast controller's browse used to open one each, and a Pi TV receiver spent ~8% of its JS thread parsing every mDNS packet on the network through them|
|`src/private-overlay.js`, `bin/private-relay.js`|Stateless 2-hop UDX-spliced guard overlay on unmodified npm `hyperdht`: Corestore-free `peartube-private-relay` forwarders (`relayTo` in RAM, zero disk writes; runs under Node or Bare) + symmetric 2-hop `createPrivateSwarm` with fresh-boot `/24`-diverse guard auto-discovery, guard-proxied pre-signed `mutablePut` descriptors, and sealed hourly rendezvous slots|
|`bin/relay.js`|Relay process, configured by env and settings. `start`/`stop` open and close the node, acquirer, cast stack and plugins; settings that are not `live` and `POST /v1/restart` reopen them in the same process (serialized, the API stays up). `stop` closes the plugin host first (a startup folder import ends between files) and keeps the node visible until then; shutdown waits up to 2 s for an open or reopen in flight, and `serial` refuses new work once shutting down. Restart also brings back a guard whose process died. The `directory` setting records what it lists in private `directory.json`, so turning it off unlists exactly those and leaves hand-listed sources (a relay without the file adopts its listed followed sources once if the setting is on, and starts an empty record if it is off). The `privateGuard` setting runs `bin/private-relay.js` as a child process (own HyperDHT, port and key; exits when the relay does) so others can route privately while the relay stays direct; `src/settings.js` refuses a fixed guard port equal to the peer port, in either order|
|`src/mirror.js`, `src/hiverelay.js`|Mirror & supplemental seeder plugin host (`http-acquire`, `channel-backfill`, `blob-rechunk`, `watch-dir`, `feed-mirror`, `p2p-replicate`, `hiverelay-seed`). `src/hiverelay.js` recruits existing `p2p-hiverelay` (`v0.24.x`/`v0.26.x`) nodes via authenticated `POST /seed-core` (`PEARTUBE_HIVERELAYS`) and zero-key `hiverelay-discovery-v1` DHT + `hiverelay-seed` Protomux requests backed by a zero-dependency 2-core Hyperdrive v11/v13 beacon|
|`src/cast.js`|`peartube-cast/v1` Cast & TV Receiver stack: `_peartube-cast._tcp` mDNS discovery, 6-char TV code + `peartube://receiver/<pubkey>?token=…` Noise P2P keypair pairing over HyperDHT, byte-exact mid-stream `HTTP -> P2P` splice proxy, and autonomous P2P receiver peer adoption (public P2P or strict fail-closed 2-hop `privateRouting` matching the cast initiator) so once a cast starts, the receiver keeps playing and seeds the video as a normal peer even when the initiator goes offline. The receiver's player (and the splice) read a known blob through `/cast/v1/p2p/<token>`: `hypercore-byte-stream` with `prefetch: false` (each reader on its own core session, since the stream closes the core it reads) plus one sliding `core.download` window, 120 s of the stream's bitrate while the disk has room, down to 20 s as free space nears a 1 GiB reserve, and never more than the disk holds above 256 MiB (below that, reads go on demand). A reader past its first 2 MiB (the player streaming, not probing a header or index) gets no more bytes while under 2 s of film lies downloaded ahead of it (10 s right after a start or seek), until 10 s does or 20 s pass (`holdIfThin`): the player waits once instead of resuming with a second in hand and stalling again. Watched blocks are trimmed only once free space falls under 4 GiB (or three full windows): every 15 s (every 3 s under the reserve) it clears what lies more than 30 s (at least 64 MiB; just 64 MiB under the reserve) behind the earliest reader, at most twice what the stream plays between passes, never while the player starts or seeks (unless the disk is nearly full), and `evictBehind` remembers where it stopped instead of counting from the film's first block. On the Pi's SSD the every-15 s clear-and-compact competed with playback, and clearing hundreds of MB right after a seek left the receiver 10 s without a byte. The stock blob server downloads from the read position to the end of the file on every `bytes=N-` request, which filled the Pi's SD card with a 77 GB film. Pairing tokens and receiver seeds stay in private files (`receiver.json`, `cast-receivers.json`), never in Corestore|
|`src/cast-ui.js`|Zero-install 10-foot Smart TV Web Receiver HTML (`/tv`, `/cast/receiver`) for LG webOS, Samsung Tizen, consoles, and kiosk browsers, with D-pad/media remote bindings and SSE/HTTP playback sync|
|`bin/receiver.js`|Portable TV Receiver daemon (`peartube-receiver` / `npm run receiver`): runs Hybrid P2P+HTTP or `--thin` (pure TCP/HTTP + mDNS, zero P2P runtime) and drives `web`, `mpv` (JSON UNIX IPC), `vlc`/`cmd:…`, or `headless` sinks|
|`android/`|Android app, which GitHub releases ship as a signed APK beside the Mac app (not part of the core line budget): Kotlin and Jetpack Compose. It runs the core itself as a peer, in a Bare worklet through bare-kit-kotlin's `Worklet`/`Ipc` (`app/src/main/java/to/holepunch/bare/kit`, vendored unchanged at the commit `worklet/bare-kit.sh` pins as `BARE_KIT_KOTLIN`; their JNI bridge is in the QuickJS `libbare-kit.so`; `proguard-rules.pro` keeps the classes the bridge calls back by name), speaking `worklet/worker.js`'s JSON lines (`Worker.kt`; `ReceiverWorker.kt` for `:tv`). It keeps the data paths of the Dioxus app it replaced (`files/settings.json`, `no_backup/trackers/<key>`, `files/soundfont.sf2`), so a release build signed with the same key updates it in place. The worklet suspends while the app is in the background (`PearTubeApp.kt`), which also holds the Wi-Fi multicast lock LAN discovery needs while the app is in front. Debug builds install beside the release app as `com.peartube.app.dev`, and so does a release build made with `-Ppeartube.dev` (signed with the debug key)|
|`android/native/`|`libpeartube.so`: the Rust player from [peartube-media](https://github.com/ayooooo123/peartube-media) (OxideAV, ported software decoders, MediaCodec and AAudio) behind JNI for `player/NativePlayer.kt`. Full VLC-format compatibility remains in development; require per-format playback evidence before claiming support|
|`android/app/src/main/kotlin/com/peartube/app/player/PlayerViews.kt`, `Letterbox.kt`, `ScreenShape.kt`|Two SurfaceViews (video, subtitles above it) behind the Compose UI, in the activity's content view, under the play screen's slot; their surfaces go to `AndroidBackend` through JNI. Old views stay attached until the native side proves it has let go of their surfaces; other screens cover them. When Android takes a Surface away (the app goes to the background), `surfaceDestroyed` waits up to 1 s for the native side to let go: a MediaCodec still stopping on a Surface that is already gone fails, its cleanup is never proved, and every later Surface is held. The picture is as large as the slot allows without losing any of it: its display shape is the coded size stretched by the pixel's shape (`PlayerState.displayAspect`, from peartube-media's `State::video_pixel_aspect`, so anamorphic video is not squeezed), and bars encoded into the frame are not counted as picture. `Letterbox` finds those from `PixelCopy` read-backs of the video surface, one per new playback position (frames drive it, no timer); it cuts nothing until six different bright frames are in, keeps everything lit in any frame, and only ever grows, so a scene that opens into the bars widens it at once. `visibleFit` (`ScreenShape.kt`) then keeps every pixel of the picture on the glass: no corner of it past a rounded screen corner's arc (`WindowInsets.getRoundedCorner`) and none of it under the camera hole (`displayCutout`), shifting it clear of the hole before shrinking it; window-inset changes re-run the layout. The video view holds the whole frame at that scale, its encoded bars falling around the picture, off the screen where the picture spans it. Black bars remain only on the axis where the picture's shape and the screen's differ. The subtitle view covers the whole slot|
|`android/app/src/main/kotlin/com/peartube/app/ui/PlayScreen.kt`|The play screen leaves its slot clear and draws the controls over the picture: back, ±10 s, play/pause, the clock, a seek bar and fullscreen, plus audio and subtitle menus. They hide 3 s after the last touch while playing; a tap on the picture brings them back. Fullscreen hides the system bars and lays the window out edge to edge, sideways for a wide picture; turning the phone sideways enters it, and back leaves it. The picture's content description carries the clock, for TalkBack and `e2e.mjs`|
|`android/tv/`|Dedicated Dumb TV Receiver APK (`com.peartube.receiver`, `PearTubeReceiver-<version>-arm64.apk`): pure 10-foot idle QR screen + `libpeartube.so` video player over the headless P2P / 2-hop `privateRouting` peer engine—zero library, channels, search, CameraX, or settings UI, with full D-pad/media-remote playback controls (Play/Pause, ±10 s, focusable seek bar, Audio & Subtitle track pickers, stream/decoder info, and Back-to-hide / Back-to-stop) synced back to the sender (`ReceiverActivity.kt`, `ReceiverWorker.kt`, `ReceiverApp.kt`). Its worklet runs on V8 (`worklet/bare-kit.sh arm64-v8a-v8`; the APK is ~70 MB). On the Pi 4 the app lives on the adopted SSD: `adb install -r` puts an update back on internal storage, so follow it with `adb shell pm move-package com.peartube.receiver <volume uuid>`; on the SD card the receiver's writes starved Android's own I/O and its watchdog restarted the system|
|`android/worklet.mjs`|Packs `worklet/worker.js` for android-arm64 with bare-pack, links its native addons with bare-link, and gathers them with bare-kit's libraries; both `:app` and `:tv` run it, and run cargo for `android/native`|
|`android/release.sh`, `android/release-tv.sh`|Build the signed arm64 release APKs (`PearTube-<version>-arm64.apk` and `PearTubeReceiver-<version>-arm64.apk`) into `android/build/release-apk`, signed with `~/.gradle/gradle.properties`|
|`android/e2e.mjs`|On a connected phone, against a live relay: a fresh install of `com.peartube.app.dev` (the debug build, or `--apk` for a `-Ppeartube.dev` release build) joins the relay's tracker through Settings, lists it, plays the first entry (video frames from SurfaceFlinger, the clock moving, AAudio started), goes fullscreen and back (the back button where it was before), and returns to the list. With `--lan` it also checks that LAN discovery runs. It stops if a system window comes to the front, such as Android's one-time "Viewing full screen" notice: someone taps Got it on the phone, then it runs again. Writes `android/build/e2e/result.json` and screenshots|
|`desktop/`|Mac app (not part of the core line budget): GPUI through `gpui-kit` (Zed's `gpui-pre` snapshot and gpui-component's widgets). It runs the same worklet as Android through bare-kit's C API (`src/worker.rs`, the same JSON lines), and the same Rust player with peartube-media's `AppleBackend`. It keeps the Dioxus Mac app's data paths: `settings.json` and `soundfont.sf2` in `~/Library/Application Support/PearTube`, each tracker's Corestore in `~/Library/Caches/PearTube/trackers/<key>`; `PEARTUBE_STORAGE` puts both in one directory. `build.rs` packs the worklet for darwin and links BareKit|
|`desktop/src/video.rs`|The picture: a native NSView under GPUI's own view (`AppleWindowSlot`), which peartube-media's `AppleBackend` draws into: an AVSampleBufferDisplayLayer on the audio renderer's synchronizer, fed by VideoToolbox for H.264, HEVC (with HDR10 mastering metadata, all-zero unknown `clli` payloads stripped, and Dolby Vision profiles 5 and 8.x carried in the format description), VP9, and AV1 on Macs that decode it in hardware (M3 and later), and by the player's software decoders for everything else, plus an sRGB-tagged subtitle layer over it. Both `preferredDynamicRange` (`"high"` vs `"standard"`, macOS 26+) and `wantsExtendedDynamicRangeContent` turn on only for PQ/HLG/Dolby Vision streams and stay in SDR (`"standard"`, `false`) otherwise, `FigImageQueue` is pre-primed with a `16x16` non-`IOSurface` `DoNotDisplay` sample at layer creation and `EnablePSEMitigation` is turned off before Frame 0 so neither `MediaToolbox` nor `WindowServer` ever washes a single pooled `IOSurface` into `#262626` grey when macOS `PhotosensitiveMitigation` is stuck on, and `preventsDisplaySleepDuringVideoPlayback` keeps the XDR panel awake. E-AC-3 reaches AVSampleBufferAudioRenderer compressed, so Dolby Atmos survives; other audio is decoded to PCM. There is no AVPlayer and no local HLS. While a video plays the window is transparent and the play screen paints nothing over its slot, so the picture shows through and the controls draw over it, the way GPUI puts a blur under a window|
|`desktop/src/play.rs`|The play screen: the controls over the picture (back, ±10 s, play/pause, the clock, a seek bar and fullscreen, plus audio and subtitle menus), hidden 3 s after the mouse last moved while playing. ## Rules

- The Corestore holds only public data (tracker + blobs). Replication serves any stored core a peer can name. Secrets, source URLs and headers stay in private files.
- `apply` is the only gate on the tracker. It must stay deterministic: no clock, no randomness, no I/O. A writer may only add or remove entries under its own writer key.
- Keep Autobee `fastForward: false`. Fast-forward adopts a peer's built view without running `apply`, which lets a forging peer plant entries under other writers' keys (covered by a test).
- A tracker write counts only once it is in the local oplog; an unsynced joiner's optimistic write lives in memory until first sync.
- Connect peers with `tracker.replicate(conn)`, not `store.replicate(conn)`; only the former attaches Autobee's wakeup protocol.
- Announce at most 24 content blobs (two swarm topics each). `status()` must never join a content topic: it is polled every few seconds, and joining there churned the DHT and evicted the titles the relay seeds. Content beyond the cap rotates one complete copy every 20 s, and eviction takes the least recently served blob (touching an announced blob on re-join), owned or cached.
- Give Autobee a namespaced store, and have a new tracker's founder append once before relying on others' optimistic writes.
- Pin `autobee` exactly; it is experimental.
- Use the Holepunch libraries (Hypercore, Corestore, hypercore-storage, Hyperswarm, HyperDHT, hypercore-blob-server) through their public API only, unmodified from npm: no monkeypatching, private methods, private fields (`core.core`, `replicator`, `bitfield`, `store.cores`, `_needsUnannounce`) or patched copies. Count and check local blocks with `core.count()` / `core.has()`, set replication windows with the `inflightRange` open option, and reach storage through the `CoreStorage` instance the node owns. No router rules (OPNsense) either. Blind relays (`relayThrough`) are optional; nothing may depend on one.
- One exception, until [holepunchto/udx-native#107](https://github.com/holepunchto/udx-native/pull/107) is released: `udx-native` comes from `ayooooo123/udx-native` branch `peartube` (`package.json` dependency plus `overrides`, like `sodium-native`). It is 1.22.0 with that PR's commits, one PearTube-only commit, and android-arm64, darwin-arm64, ios-arm64 and ios-arm64-simulator prebuilds built from it (the other targets, including the relays' Linux, keep 1.22.0's binaries). Stock 1.22.0 drops a framed HyperDHT stream to one JS call per UDP packet (~1.4 KB) the first time a packet spans two frames: 92,560 calls for 128 MiB on a Mac against 2,076 patched. On the Pi 4 receiver (QuickJS) the JS thread was pegged at ~46 Mbps and a ~63 Mbps film played at half speed; patched it took in up to 152 Mbps. The PearTube-only commit keeps read buffers at 60 KiB, under the 64 KiB allocator classes (allocating 68 KiB took ~87 µs against ~46 µs for 60 KiB on the Pi). It's tuned for one platform's allocator, so it stays out of the PR. When a release carries the PR, go back to the npm version and drop the override, and with it the 60 KiB buffers.
- A second exception, while it soaks before an upstream PR: `hypercore` comes from `ayooooo123/hypercore` branch `peartube` (dependency plus `overrides`), 11.39.5 plus one commit. A busy peer hotswaps (re-requests a block already in flight elsewhere) only once the block has been in flight 3× that peer's recent block round trip; an idle peer still takes any, so a block stuck at a slow peer is rescued. Stock `getMaxHotswapInflight()` is at least 16, above our windows (TV and phone [6, 8], relays [12, 32]), so every peer kept standing duplicate requests: 25–30% of what the Pi received, and 200 blocks arrived as 394 in Hypercore's own test with an [4, 8] window (205 with the fix). Raising our windows to 16 removed the waste but also the rescue: one block stuck at a slow peer stalled the Pi for 69 s (and a phone for 42 s). With the fork the Pi played 404 s of Avatar from a cleared cache in 414 s (one 8 s start, no stalls), 97% of received bytes new. Hypercore's `test/all.js` passes (445/445).
- Upstream contributions (to Holepunch or anyone) go up as a single commit we're sure of: squashed, tested on its own, and described by its final state. Keep tuning for one platform or device (an allocator's size classes, one SoC) out of them; it stays in our fork, labelled as ours.
- Plugin Protomux channels (`hiverelay-seed`, `peartube/bulk-busy`) register `mux.pair()` on every connection. Protomux rejects an open for an unpaired protocol, so without it a side that attaches later never gets the channel.
- Never pause a replication connection (`conn.pause()`) for long enough to trip Protomux's 10 s timeout, and never pause a PearTube relay: a connection paused past its timeout loses its Hypercore peers and downloads on it stall for good. Relays coordinate backfill with `peartube/bulk-busy` (triggered by both P2P and `/v1/blob` HTTP viewers) instead; the pause cap is only for HiveRelays, pulsing them at ≤ 0.5 Mbps (≤ 6 s pause) while human viewers stream.
- Open owned video cores' write and HTTP-warm sessions with `active: false` (`put`, `/v1/blob`), and attach 4-cursor 16 MiB parallel `libuv` upload read-ahead via `store.watch` (`weak: true`, skipped for `bulkPeers`) when Corestore wakes an owned per-video core. An owned core never downloads; an active session makes it report "downloading" for Hypercore's 20-40 s linger, and without `store.watch` per-video cores missed `blobSlots`' upload read-ahead and stalled concurrent 4K viewers on spinning disks.
- Clamp cached foreign video cores shut at rest (`cachedBlobs` + `cachedByDiscovery` in `src/index.js`), collar open `blobCores` (`6` on worklets, `24` on relays), and starve client worklet RocksDB caches (`blockCache: false`, `tableCacheIndexAndFilterBlocks: false`, `pinningTier: 0`, `maxOpenFiles: 48`, `writeBufferSize: 12 MiB` mobile / `32 MiB` macOS with `maxBackgroundJobs: 3/4`, `treeCache: 512`) so 50+ GB libraries ride OS page cache wet and light without RocksDB memtable write stalls.
- Collar followed channels to an `O(1)` active `Autobee` + overlay-topic pool (`maxActiveSources`: `8` on worklets, `24` on relays), persisting hibernated channel snapshots in private `0600` `catalog-cache.json`, waking focused channels on demand (`focusSource` / `search(id, { source })`), rotating dormant channels in the background, and checking `storedDisc` from `coreStorage.createCoreStream()` + `store.watch` so `1,000+` channels (`50,000+` videos) boot in `<300 ms` without opening `1,000` `Autobee`s or `hasCore()` queries. The background rotator must **not** be gated on being over the cap: it refreshes every awake channel's view each tick and wakes the dormant ones even under the cap, every 1.5 s while anything is unhydrated and 15 s after. A phone follows one channel, so the cap is never reached there, and gating on it left the library a frozen snapshot: `search()` with no source filter never wakes a hibernated channel, so nothing refreshed it and the app listed blob keys the publisher had already repointed.
- Give `hyperdht` nothing for `bootstrap` unless the user set their own: its built-in table (`node1..3.hyperdht.org`) is the one that stays current. The Android app used to resolve `bootstrap1..3.hyperdht.org` itself and pin `:49737`; those names resolve to hosts the DHT stopped answering on (`167.71.129.94`, `35.209.238.143` against the live `88.99.3.86`, `142.93.90.113`, `138.68.147.8`), so the phone never joined the public swarm at all — `public: { peers: 0, rxBytes: 0, txBytes: 0 }` while its LAN replicated fine. A phone with no public peers can only replay what LAN peers hold, which is how a channel's newest writer cores go missing and a video that exists in the feed never appears on it. `desktop/src/worker.rs` already passes nothing (`non_empty`); the phone must match.
- Autobee emits `'update'` only on an interrupt. To hear about view changes, pass `onchange` to `createNode`, which runs from Autobee's `update` handler.
- The background tick must **read** each awake channel's view, not just compare versions: walk the view with `refreshSourceCache(src, { force: true })`. Walking is what makes Autobase fetch the blocks it linearizes next, so gating the read on `view.version` deadlocks a follower mid-sync — no read, no progress, no new version. Before this, a follower of the Unraid channel stopped at 555 announces / 359 entries and a fresh Bare node did the same while the publisher held 542 (Interstellar included); with the forced read it goes 555 → 778 announces → 542 under two minutes. Reads are bounded by the pool, so this costs at most `maxActiveSources` scans per tick.
- A node that is playing must not fetch ahead for peers: `attachUploadWarmth`'s upload handler returns early while `setPlayerActive(true)` holds, and the apps set it on play and clear it on leaving the player. Peers still get every block on demand; only the 32–128-block read-ahead stops. Without it a laptop seeding 8.65 MB/s to a phone while decoding a 4K film buffered its own picture.
- A followed channel's snapshot must rescan when its own `bee.update()` finishes, even if Autobee emitted no `update` interrupt: keep `dirty` alongside the revision, and compare the public `Hyperbee.view.version` after every applied read. Check both before hibernation, too. Otherwise an old `catalog-cache.json` keeps pointing at purged legacy `blobSlots` after the publisher repoints a video to a per-video core; the phone lists a movie whose HTTP Range never returns a byte.
- Reads of a tracker view (`search`, `findEntry`, `discoveredSources`, `publishedSources`) wait at most 1 s for Autobee (`applied()` in `src/index.js`), and so does the apps' worklet at startup. A fresh joiner of the Unraid tracker took ~2 minutes to catch up in Node on a Mac and far longer on a phone's QuickJS; before this, the 5a sat on "Connecting…" and every search hung until then. Writes, garbage collection (`hasLiveBlobReference`) and a relay's startup scan of its own videos still wait for the full update; a second owner scan runs once the tracker has caught up.
- Don't add a machine API field without updating every client in the same change. MediaStorm is the proof client.
- Prefer deleting code to adding it. Old platform code is at tag `archive/v0.3.0-platform`.
- `src/index.js` also runs under Bare, in the apps' worklet: no Node-only imports there. Map `node:` builtins to `bare-*` in `package.json` `imports`, except `node:crypto`, which goes to `worklet/crypto` (SHA-256 only).
- The Android and macOS worklet runs on QuickJS, except the TV receiver's, which runs on V8: no `Intl`, and guard V8-only APIs such as `Error.captureStackTrace`. Keep `worklet/patches/libqjs-function-source.patch` until libqjs ends its CommonJS wrapper on a new line; without it the worklet dies loading bonjour-service, which `test/desktop.e2e.js` catches.
- Keep `worklet/patches/libqjs-deferred-release.patch`. QuickJS frees an object as soon as its last reference goes, but addons built for V8 release a reference and then touch memory that object owned (jstl's `js_persistent_t::reset()`). Without the patch, udx-native's DNS lookup crashes the worklet whenever HyperDHT resolves a bootstrap host by name. `test/desktop.e2e.js` names its bootstrap nodes `localhost:<port>` to catch it.
- Keep `worklet/patches/quickjs-weakmap-ephemeron.patch`. QuickJS scans `WeakMap` values unconditionally rather than as ephemerons and ignores `libqjs`'s external `ArrayBuffer` allocations in `js_trigger_gc`, so every closed `bare-http1` socket (`_connections.set(socket, conn)` where `conn._socket = socket`) and `bare-url` `URLSearchParams` leaked its 64 KiB read buffer and arenas forever.
- Keep `worklet/patches/libqjs-weak-reference-delete.patch`. `libqjs` defined `[Symbol("__native_reference")] -> External(js_finalizer_t)` with `flags = 0` (non-configurable) in `js__set_weak_reference`, so `JS_DeleteProperty` in `js__clear_weak_reference` silently returned `0` (`FALSE`) on every `jstl` `js_persistent_t::reset()` in `rocksdb-native` and `udx-native`, leaking ~4 KB per RocksDB read/write and swelling `PearTube.app` past 2 GB.
- Keep the Android app's `minSdk` at 29: the QuickJS bare-kit calls `timespec_get`, new in API 29, and the player calls NDK media functions added in 29. Both apps' version is `package.json`'s; releases bump it there.
- Keep the Android app's native libraries uncompressed in the APK (`jniLibs.useLegacyPackaging = false`). Android then loads them from the APK; compressed, it unpacks a second copy at install, which made the Dioxus app take 61 MB on the phone for an 18.7 MB APK. bare-kit loads the worklet's addons by file name, which works from the APK.
- Keep mimalloc as `libpeartube.so`'s global allocator (`android/native/src/lib.rs`). The software decoders allocate and free a lot each frame: on a Pixel 5a, 720p XviD took 23 ms a frame with Android's own allocator and 11 ms with mimalloc, and the MPEG-4 Part 2 decoder's second rebuild thread made decoding slower with Android's allocator. It uses local-dynamic TLS because the app loads the library with dlopen.
- Pin `gpui-kit` exactly: it pins its own GPUI snapshot, and GPUI's API changes between snapshots.
- Keep the Mac app's picture in its own NSView under GPUI's view (`desktop/src/video.rs`), with the window transparent only while a video plays. A layer inside GPUI's view would be drawn over by GPUI's Metal layer, and a view or child window above it would cover the controls in fullscreen.

## Testing

- Never write unit tests after you write code.
- Highly prefer E2E tests as the sole testing mechanism. Use them to verify complex features work. At the end of E2E tests, produce a verifiable and repeatable artifact.
- Phone tests drive only the app. When a system window is in front (a permission prompt, Android's fullscreen notice), stop and ask the user to answer it; never tap it or send it keys.
- Headless browser runs (`test/*.e2e.js` and throwaway CDP smoke scripts alike) must always pass `--use-mock-keychain --password-store=basic --disable-sync --disable-features=BraveWallet,BraveRewards,BraveNews` and kill the browser process on teardown, so macOS never blocks an unattended run behind a Keychain dialog.
- Clear a TV receiver's downloaded video before every measured playback test, or the run replays from its disk and says nothing about the network: stop the app, delete `<dataDir>/no_backup/cast/corestore` (and any `peer-*`), keep `receiver.json` (its pairing identity), start it again. The Pi runs a userdebug build, so `adb root` reaches the app's data on the adopted SSD. Pick a stretch and check that the cached bytes grow while it plays.
- If you must test a system in isolation, first write down all the ways it could fail, then write the code.

## Installing a Relay on a System

Follow `README.md` (`### Install on a system (agent quickstart)`) when asked to stand up `peartube-relay`:

- **Environment fit**: Real Linux/macOS hosts, NAS boxes, VPSes, and self-hosted remote `codex` CLI / SSH sessions work, provided command sandboxes (`codex-network-proxy`, Landlock/Seatbelt) are escalated so `udx-native` can open raw UDP sockets and the service is detached under Docker (`--restart unless-stopped`), `systemd`, or `launchd` (never leave `npm start` attached to an agent shell turn). **OpenAI-hosted Codex Cloud VMs (`Work in > Cloud`) cannot run a public/LAN relay**: their HTTP/HTTPS-only proxy blocks raw `HyperDHT`/`UDX` UDP even over Tailscale, exposes no inbound ports, and suspends VMs between turns—use `createTestnet()` on `127.0.0.1` for tests or deploy `ghcr.io/ayooooo123/peartube-relay:latest` to a real host.
- **Required settings**: Set `PEARTUBE_STREAM_HOST=<reachable-ip>` (never leave `127.0.0.1` for remote viewers), set `PEARTUBE_LAN_HOST=<lan-ipv4>` on LAN hosts (`--network host` in Linux Docker so mDNS `224.0.0.251:5353` and ephemeral UDP cross out of the container), and set `PEARTUBE_API_TOKEN=$(openssl rand -hex 32)` on any non-loopback network (`0600` env file, `0700` `PEARTUBE_STORAGE`).
- **Native host dependencies**: Node `>= 22` and `git`. The add-ons and `bare` need only glibc, libm, libstdc++ and libgcc_s (`rocksdb-native` linked `libatomic.so.1` up to 3.18 and no longer does from 3.19). `npm ci --omit=dev` links `node_modules/.bin/bare` directly to the native `bare-runtime` binary so `ExecStart=.../node_modules/.bin/bare .../bin/relay.js` receives `SIGTERM` cleanly without a Node wrapper. The Docker image needs none of this at runtime: Node runs only in its build stage (which keeps only `linux-<arch>` add-on prebuilds, drops `.node` builds and moves `bare` out of `bare-runtime-*`), and the relay image is `gcr.io/distroless/cc-debian12` (glibc, libstdc++, libgcc_s, CA certificates) with `bare` as PID 1. Its build loads every native add-on under Bare, so a dependency that needs a missing library fails the build. There is no VPN support in the image or the relay; run a VPN outside the container if you need one.
- **Verify before yielding**: Poll `GET http://127.0.0.1:8174/v1/status` for 64-hex `tracker` + `channel` keys and check `GET /manifest.json` (`200 OK`).

## Troubleshooting

No peers: check both NATs. HyperDHT aborts with `HOLEPUNCH_DOUBLE_RANDOMIZED_NATS` (reported as `HOLEPUNCH_ABORTED`) when both sides are randomized; forward a UDP port (`PEARTUBE_DHT_PORT`) or use `PEARTUBE_RELAY_THROUGH`.

Slow first connection on a local testnet: every peer is on 127.0.0.1, which HyperDHT will not holepunch, so two peers connect only once one of them passes dht-rpc's NAT check and reports itself open. That check can take minutes after a failed first try; a fresh testnet usually connects in about 25 seconds, which is why the E2E tests wait up to 60–120 seconds.
