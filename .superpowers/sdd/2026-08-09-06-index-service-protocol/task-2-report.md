## Server/client authentication contract

The role split is explicit rather than inferred:

- `attachIndexServiceProtocol` is the server constructor. It requires `limits.localTransportPublicKey`, supplied from the owning swarm/runtime identity, and refuses to serve unless that trusted 32-byte key exactly equals the signed announcement transport key. It separately requires the live 32-byte `connection.remotePublicKey` for authenticated peer identity/admission. It does not infer a server role and does not trust mutable connection metadata as a substitute for the configured local identity.
- `createIndexQueryClient` is the client constructor. For every caller-owned connection it requires live `connection.remotePublicKey === announcement.transportPublicKey` before creating the query channel. Service context is held by this explicit client instance, not hidden on the connection and not kept in a global WeakMap.
- A retained scoped runtime is also a client: `retainIndexService` constructs a configured client factory from the verified announcement and limits but opens no protocol channel eagerly. `queryIndexService` requires an active caller-owned connection whose authenticated remote Noise key equals the retained announcement transport key, then uses that configured client to initiate the exact protocol/topic channel. The runtime joins only that direct peer and never serves a local store or registers a wildcard index responder.

Both sides reuse the Task 1 topic, signed announcement verification, explicit monotonic sequence state, scoped hello/capability negotiation, replay monotonicity, admission, expiry, and caller-owned connection lifecycle. The shared scoped hello/session primitives were moved unchanged into a cycle-free `network/scoped-protocol.js` module so the explicit index protocol and generic runtime use one implementation.

## Store revision and paging design

`createIndexerStore` now exposes `queryIndexPage({ selectors, limit, continuation, sourceRevision })` through the existing serialized durable facade. It does not expose raw HyperDB or accept a client checkout/offset.

The schema surface captures `${core.fork}:${core.length}` from the durable index Hypercore at the serialized transaction snapshot. That value is the returned `sourceRevision`; it survives facade/process restart because it comes from the durable core rather than a process-local counter. A continuation request must present the exact prior revision, and any fork/length change is rejected with `INDEX_QUERY_STALE_REVISION` before rows are returned.

Paging uses complete compound-key continuations:

- exact external reference: `(namespace, normalizedIdentifier, publisherId, sourceRecordRef, entityKind, entityId)`;
- title-token prefix: `(relationType, fromId, publisherId, sourceRecordRef, toId)` within the bounded `title-token` prefix range.

Each selector reads at most `remaining page capacity + 1` rows from the durable index. The extra row determines whether another page exists. No offset is accepted, no prior rows are allocated merely to skip them, and all selectors in one page execute inside one serialized snapshot transaction. The wire cursor is only an unguessable fixed token. Its responder-local bounded table stores the exact indexer ID, canonical selector set/query modes, durable revision, complete validated continuation key, and expiry. Reuse for another selector set/indexer, after token expiry, or after the durable revision changes returns `INVALID_CURSOR`.

## Protocol lifecycle
The responder service also enforces a bounded physical execution budget keyed to the exact store facade. Logical cancellation/timeout/channel close aborts the passed signal and drains wire state, but the execution token remains charged until the underlying store promise actually settles. The production store checks that signal before snapshot work, before each selector scan, and after each durable read.

The server accepts only `index-query-request` and `index-query-cancel` after the authenticated scoped hello. The client accepts only `index-query-page` and `index-query-error`. All four names are registered in `PEER_FRAME_TYPE_NAMES`, so a fresh remote process decodes their stable numeric codes without relying on same-process encode side effects. A raw-frame regression covers that property.
The server dispatcher and client requester each maintain one timer and one tracked entry per live query plus a bounded settled-query-ID replay window covering the maximum deadline/late-frame interval. Sequential ID reuse is rejected, so a late page cannot settle a newer request. Success, remote error, local deadline, AbortSignal cancellation, explicit cancel, policy suspension, channel close, service release, announcement expiry, and client/server/runtime close remove exactly the live entry and clear timers/listeners; close also clears tombstones and responder cursors. Policy suspension keeps tombstones and the authenticated channel live while sending cancels and draining pending work. The server aborts its internal controller. Store results and remote pages arriving after settlement are ignored. Channel/connection close remains terminal for the attachment. Teardown closes only protocol channels; it never closes/destroys caller connections, Corestore, or index store.
Each side maintains its own monotonic peer-frame request IDs. Query pages/errors correlate only by the exact codec `queryId`. The server bounds pending queries, validates announced capabilities for every selector mode, decodes/validates cursors, dispatches only through `indexStore.queryIndexPage`, maps rows to unranked source-attributed wire results, and sends bounded structured errors. Unknown store errors become generic `INTERNAL_ERROR`; their messages and data are not exposed.

The production retained-service path stores an explicit configured `createIndexQueryClient` and no generic runtime index session. Its requester is created per caller-owned authenticated connection when `queryIndexService` initiates the query channel; page/error frames flow into that requester by exact `queryId`. Network-policy disable suspends the configured client and drains its pending work without closing the channel; enable resumes it. Release, identity-changing supersession, expiry, and runtime close remain terminal and close the configured client and all sessions. A real paired-Protomux regression registers the explicit service responder first, retains the service on a separate consumer runtime, emits the authenticated service connection, and queries it through `runtime.queryIndexService`.
Monotonic same-channel announcement supersession is bound to exact indexer ID plus transport key. The responder and configured client both verify and commit the newer signed sequence through their original persistent sequence state, replace expiry timers transactionally, and preserve the active Protomux channel; same/older sequences or timer-setup failures leave sequence/configuration/timers unchanged. Capability-set changes refresh the responder dispatcher's allowed selector modes in place. Refreshed safe limits configure future client sessions, while already-negotiated live channel frame bounds remain unchanged. A transport-key or indexer-ID change remains a terminal cutover; if no client exists while policy is disabled, the retained newest announcement is used when a client is later created.


Optional query telemetry is restricted to `{ code, count, durationMs, capability }`. It never includes query IDs, titles, external identifiers, tokens, selectors, cursor contents, store errors, or result bodies.
